# 스프린트 리뷰 예상 Q&A (프론트엔드 파트장용)

알바로그(albalog) 프론트엔드 기준으로 예상 질문과 답변을 정리했습니다.

---

## 1. 스코프 / 완료 범위

**Q. 이번 스프린트에서 프론트에서 실제로 완료한 건 뭐가 있나요?**

- **A.**  
  - **인증·온보딩**: 로그인 랜딩, Google OAuth, 회원가입, 지역 온보딩  
  - **홈**: 오늘 근무 요약, 근무 리스트, 빠른 액션, 추천, 알림 요약, 일정 추가·지도 모달  
  - **스케줄**: 월간/주간 뷰, 일정 추가·수정·삭제, 작업장 추가, 오른쪽 사이드바(이번 달 요약, 오늘 일정, 알림), 빈 상태·날짜 클릭 팝업(알바 N건, 편집)  
  - **수입**: 실제 수입·예상 수입·목표 달성률·수입 분류 차트(Recharts), 정산 테이블(전체/정산 대기/정산 완료/미정산 필터)  
  - **아르바이트**: 구인 목록, 필터, 상세, 지원 확인·지원 현황·지원 관리, 리뷰 작성/보기  
  - **프로필·설정**: 프로필 보기/수정, 내 리뷰, 설정  
  - **UI**: Figma 기준으로 사이드바·헤더·수입 대시보드·정산 테이블 스타일 적용, 더미 데이터 보강  

  “완료”는 **현재 백엔드 없이 localStorage/sessionStorage + 더미로 동작하는 범위**까지입니다.

---

**Q. 백엔드 API는 연동했나요?**

- **A.**  
  아직 연동하지 않았습니다.  
  - 인증·유저·일정·수입·구인·리뷰 모두 **로컬 저장소(localStorage/sessionStorage) + 시드/더미 데이터**로만 동작합니다.  
  - Custom Hooks(`useUser`, `useJobs`, `useIncome`, `useHomeData` 등)로 데이터 접근을 추상화해 두었기 때문에, 이후 API가 정해지면 **Hook 내부만 교체**하면 됩니다.

---

## 2. 기술 스택 / 선택 이유

**Q. React 19, Vite 7 같은 최신 스택을 쓴 이유가 있나요?**

- **A.**  
  - **Vite**: HMR 속도, 빌드 속도 때문에 선택했습니다.  
  - **React 19**: 프로젝트 시작 시점에 19가 안정화되어 있어, 최신 훅·동시성 등 나중에 활용할 수 있도록 맞춰 두었습니다.  
  - **Tailwind v4**: 디자인 시스템(색, 간격, 폰트)을 빠르게 맞추기 위해 사용했고, Figma 톤에 맞춰 인디고/슬레이트 계열로 정리했습니다.

---

**Q. 상태 관리는 어떻게 하고 있나요? 전역 상태 라이브러리는요?**

- **A.**  
  - **페이지/기능 단위**: 각각 `useState` + `useEffect`로 로컬 상태와 localStorage 동기화만 하고 있습니다.  
  - **전역 상태 라이브러리(Redux, Zustand 등)** 는 아직 도입하지 않았습니다.  
  - 이유:  
    - 데이터 소스가 아직 “로컬 저장소” 하나라서, 복잡한 전역 상태가 필요하지 않았고,  
    - API 연동 후 **서버 상태는 React Query(TanStack Query)** 로 가져가고, **진짜 전역 클라이언트 상태만** 최소한으로 두는 방향을 고려 중입니다.

---

**Q. 수입 차트는 어떤 라이브러리로 구현했나요?**

- **A.**  
  **Recharts**를 사용했습니다.  
  - PieChart로 “매장별 수입 비율”을 보여주고,  
  - 반응형을 위해 `ResponsiveContainer`로 감싸서, 부모에 고정 높이를 주어 레이아웃이 깨지지 않도록 했습니다.

---

## 3. 아키텍처 / 코드 구조

**Q. 데이터 레이어(API 나오면)를 어떻게 나갈 계획인가요?**

- **A.**  
  - **지금**: 페이지/컴포넌트에서 **Custom Hooks**만 사용합니다.  
    - 예: `useIncome()` → `completedWorks`, `incomeByStore`, `updateSettlementStatus` 등  
  - **이후**:  
    - API 호출·캐시는 **React Query**로 처리하고,  
    - “API 클라이언트(axios/fetch 래퍼)”는 `src/api/` 또는 `src/services/`에 두고,  
    - 기존 Hook이 그 서비스/API를 호출하도록 **Hook 내부만 교체**하는 식으로 갈 예정입니다.  
  - 페이지/컴포넌트 시그니처는 최대한 유지해서 변경 범위를 줄이겠습니다.

---

**Q. 타입 정의는 어디서 관리하나요?**

- **A.**  
  `src/types/`에서 도메인 단위로 관리합니다.  
  - `work.ts`: Work, WorkStatus, ApplicationStatus, **SettlementStatus**  
  - `schedule.ts`: ScheduleItem, Workplace, DaySummary, ScheduleType, SalaryType  
  - `notification.ts`  
  - API 스펙이 나오면 여기 타입을 **백엔드 DTO/스키마에 맞춰 확장**하고, 공통 타입은 한 곳에서만 import 하도록 할 예정입니다.

---

## 4. 이슈 / 트러블슈팅

**Q. 스프린트 중 실제로 겪은 이슈와 해결 방법이 있나요?**

- **A.**  
  - **수입 분류 차트가 안 보이던 문제**  
    - 원인: Recharts `ResponsiveContainer` 부모에 명시적 높이가 없어서, 높이 0으로 렌더됐고, 그리드 세 번째 열이 줄어들며 차트 영역이 잘리기도 했습니다.  
    - 조치: 차트를 감싼 div에 `height: 256px`, `min-height: 256px` 지정, 그리드/카드에 `min-w-0` 적용해 공간을 보장하고, 데이터가 없을 때도 “데이터 없음” 1건으로 Pie를 한 번은 그리도록 수정했습니다.  
  - **정산 테이블 타입 오류**  
    - `Work`에 `settlementStatus`, `actualPay`가 없어서 타입 에러가 났고, `types/work.ts`에 `SettlementStatus` 타입과 해당 필드를 추가해 해결했습니다.  
  - **수입/스케줄 더미 데이터**  
    - 수입·정산·차트가 비어 있으면 체감이 어려워서, `jobData`에 완료·승인 작업을 많이 넣고, 스케줄/작업장은 `scheduleSeed`로 시드해 두었습니다.  
    - `localStorage`가 비어 있을 때만 시드/더미를 넣어서, 실제 사용 데이터가 있으면 덮어쓰지 않도록 했습니다.

---

**Q. Figma와 실제 구현이 다른 부분이 있다면?**

- **A.**  
  - 대부분 **색상·간격·타이포·버튼/카드 스타일**은 Figma 기준으로 맞춰 두었습니다.  
  - **반응형(태블릿/모바일)** 은 아직 완전히 맞추지 않았고, 브레이크포인트(`md:`, `lg:` 등)만 일부 적용한 상태입니다.  
  - “목록” 뷰(스케줄)는 버튼만 두고 동작은 아직 구현하지 않았습니다.  
  - 이후 스프린트에서 반응형과 “목록” 뷰를 순차적으로 반영할 예정입니다.

---

## 5. 성능 / UX

**Q. 초기 로딩이나 리스트가 많을 때 성능 이슈는 없나요?**

- **A.**  
  - **현재**: 데이터가 전부 로컬이고 리스트 크기가 크지 않아서, 별도 가상화나 코드 스플리팅은 하지 않았습니다.  
  - **예정**:  
    - API 연동 후 리스트가 길어지면 **가상 스크롤(react-window 등)** 검토,  
    - 라우트 단위 **코드 스플리팅** 적용해 초기 번들 크기를 줄이는 방향으로 계획 중입니다.

---

**Q. 접근성(a11y)은 고려했나요?**

- **A.**  
  - 버튼/링크에 `aria-label`을 필요한 곳에만 부분적으로 넣었고,  
  - 키보드 포커스·스크린 리더 대응은 아직 전면적으로 하지 않았습니다.  
  - 다음 스프린트에서 **포커스 관리·시맨틱 마크업·aria 속성**을 단계적으로 보강할 예정입니다.

---

## 6. 다음 스프린트 / 백로그

**Q. 다음 스프린트에서 프론트 우선순위는 뭔가요?**

- **A.**  
  1. **백엔드 API 연동**  
     - 인증(로그인/토큰 갱신), 유저, 일정, 수입, 구인, 리뷰 API 스펙 확정 후 Hook·API 레이어 구현  
  2. **수입·프로필 데이터 소스 통일**  
     - 수입/정산/차트, 프로필/리뷰 화면의 더미 제거 후 API로 전환  
  3. **반응형 및 “목록” 뷰**  
     - 스케줄 목록 뷰 구현, 모바일/태블릿 레이아웃 정리  
  4. **에러/로딩 처리**  
     - API 실패 시 재시도·에러 메시지·로딩 스피너 등 공통 패턴 정리  

---

**Q. 다른 팀(백엔드, 디자인)에 요청하고 싶은 건 있나요?**

- **A.**  
  - **백엔드**:  
    - 인증 방식(JWT refresh 포함)과 **REST/GraphQL 스펙(엔드포인트·요청/응답 형식)** 을 공유해 주시면, 그에 맞춰 API 클라이언트와 Hook을 설계하겠습니다.  
  - **디자인**:  
    - 수입/스케줄의 **모바일 뷰**와 “목록” 뷰 화면이 나오면, 그 기준으로 반응형을 맞추겠습니다.

---

## 7. 협업 / 프로세스

**Q. Figma 디자인 반영은 어떻게 했나요?**

- **A.**  
  - 공유받은 Figma(알바로그)를 기준으로 **색상·타이포·간격·컴포넌트 구조**를 맞췄습니다.  
  - 레이아웃(사이드바·헤더·수입 대시보드·정산 테이블·필터 탭·필 스타일)은 픽셀 단위까지는 아니어도, 톤앤매너와 정보 구조는 Figma와 동일하게 가져갔습니다.  
  - 세부 수치는 Tailwind 유틸과 `font-['Pretendard']` 등으로 맞춰 두었고, 디자인 시안이 바뀌면 해당 컴포넌트만 수정하면 되도록 구성해 두었습니다.
